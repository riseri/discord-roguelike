# Architecture

## Overview

The project is a turn-based roguelite intended to eventually run as a Discord Activity.

The game should be separated into independent layers so that core game logic does not depend on presentation, networking, persistence, or Discord.

## Repository Structure

```text
discord-roguelike/
│
├── game-core/
├── game-server/
├── activity-client/
├── game-data/
└── docs/
```

## Modules

### game-core

Pure Kotlin game simulation.

Responsibilities:

- Combat
- Game state
- Abilities
- Enemies
- Status effects
- Relic behavior
- Dungeon state
- Run state
- Seeded random behavior
- Game events

`game-core` must not depend on:

- Spring
- HTTP
- WebSockets
- Discord SDK
- React
- Phaser
- Databases
- Persistence frameworks

`game-core` should be deterministic and easy to unit test.

### game-server

Kotlin + Spring Boot.

Responsibilities:

- REST API
- WebSocket communication if needed
- Authentication
- Persistence
- Player accounts
- Run lifecycle
- Meta progression
- Loading game data
- Connecting clients to game-core

`game-server` may depend on `game-core`.

`game-core` must never depend on `game-server`.

### activity-client

TypeScript + React.

Phaser may be used for graphical combat scenes.

Responsibilities:

- Rendering game state
- User input
- Menus
- Hub UI
- Route selection
- Combat presentation
- Animations
- Sound
- Discord Activity integration

The client should not contain authoritative game rules.

The server and game-core determine valid game state.

### game-data

Contains content definitions.

Examples:

- Abilities
- Enemies
- Relics
- Events

Content should be data-driven where doing so keeps the implementation simple.

Do not create overly generic systems solely to avoid writing specialized code.

## Dependency Direction

```text
activity-client
      |
      v
game-server
      |
      v
game-core
```

Dependencies should not point upward.

## Core Game API

Game state should be modified through explicit actions.

Conceptually:

```text
GameState + GameAction -> ActionResult
```

Example:

```kotlin
interface GameEngine {
    fun execute(
        state: GameState,
        action: GameAction
    ): ActionResult
}
```

An `ActionResult` should contain the updated state and the events generated by the action.

Example:

```kotlin
data class ActionResult(
    val state: GameState,
    val events: List<GameEvent>
)
```

## Game Actions

Use sealed interfaces or equivalent closed domain types where appropriate.

Examples:

```text
UseAbility
ChooseRoom
SelectReward
ResolveEventChoice
```

## Game Events

Actions should produce events describing what happened.

Examples:

```text
DamageDealt
BlockGained
StatusApplied
EntityDefeated
AbilityUsed
RelicTriggered
CombatWon
```

The frontend can use these events for animation and presentation.

## Randomness

All gameplay randomness must be deterministic.

Every run has a seed.

Do not call global/default random functions directly inside game logic.

Random behavior should use a seeded RNG associated with the run.

This allows:

- Reproducible bugs
- Deterministic tests
- Replay/debugging support
- Daily seeded runs later

## State

Prefer explicit immutable state transitions where practical.

Avoid hidden global state.

Prefer:

```text
old state
+ action
= new state
```

over objects mutating unrelated state internally.

## Persistence

The core engine should not know whether state is stored in:

- Memory
- PostgreSQL
- Redis
- Files
- Any other persistence system

Persistence belongs outside `game-core`.

## Design Principle

Prefer the simplest implementation that supports the current MVP.

Do not build infrastructure for speculative future systems unless the current design requires it.
